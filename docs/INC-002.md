# INC-002: Training portal unavailable by hostname

> Retrospective simulated ticket based on the completed lab. Requester, impact and priority are fictional; this was not a production support interaction.

|---|---|

| Service | Training Staff Portal |
| URL | http://staffportal.test:8000 |
| Symptom | Browser connection refused |
| Simulated impact | One user cannot access the training portal |
| Lab priority | Medium, subject to urgency and workaround assessment in a real incident |
| Status | Resolved in lab |

## Investigation sequence

1. Confirmed initial access by IP address and hostname.
2. Deliberately changed the local hosts entry from 127.0.0.1 to 127.0.0.2 and flushed the resolver cache.
3. Reproduced the browser failure while leaving the web server running.
4. Compared HTTP requests: direct IP returned 200 OK; hostname connection failed.
5. Inspected system resolution and the hosts entry. Both showed 127.0.0.2.
6. Corrected the entry to 127.0.0.1, flushed the cache and repeated the hostname request. It returned 200 OK.
7. Confirmed expected page content in Edge using the hostname URL.

## Resolution

Corrected the deliberately introduced local hostname mapping. No server restart, password change, public IP or Azure network-rule change was used. The analyst validated recovery directly; no independent end-user confirmation occurred.

## Cause and scope

The local hosts entry directed requests to an address where this server was not listening. This was not a demonstrated DNS server failure. Tests involved one VM and a loopback-bound server; wider network availability was not established.

## Escalation considerations

In production, escalate centrally managed settings, multiple affected devices, unexpected or suspicious mappings, failed direct-IP tests, or issues outside Level 1 authority. Provide impact, exact error, URL, comparisons, resolved destination and configuration evidence. Determine a mapping's intended purpose before altering it.
